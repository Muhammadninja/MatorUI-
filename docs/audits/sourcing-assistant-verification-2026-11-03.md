# Sourcing assistant verification

Inspection of 2026-11-03, for the backend owner. No sourcing request was created and no staff were notified.

## Update after this inspection

The results below record what the inspection found. Since then:

- **Decisions:** guests can chat and browse, a sourcing request requires the existing phone OTP sign-in, and the 15-minute promise is being removed.
- **Contract:** `docs/backend-sourcing-contract.md` is the current version, and it replaces the "needed" notes below wherever they differ.

- **Live test:** blocked. See the end of this report.

## Short answer

**The "purchasing team / 15 minutes" message is a confirmation that a ticket exists, not an AI reply and not a fallback.** It is fixed text, `CANONICAL_RESPONSES.CREATE_SOURCING_TICKET` in `Backend/src/common/i18n.util.ts:22`. The server sends it only after creating a ticket or finding a recent duplicate (`ai-chat.service.ts:137-170`).

**The promise it makes isn't backed up.** "Свяжется с вами в течение 15 минут" has no contact details behind it and no timer. A guest can never be reached.

## Findings for the backend owner

### A. A similar promise can appear with no ticket

The system prompt tells the model to say the sourcing department will respond within 15 minutes (`ai-chat.service.ts:228`). If the model classifies a part request but extracts no part name, or returns `GENERAL_QUESTION`, its own text goes to the customer with no ticket (`:102`). This comes from reading the code and wasn't reproduced.

The app can't tell these apart, because it ignores `intent` and `ticket_id`.

**Needed:** remove that line from the prompt, so only the fixed text can make the promise.

### B. Nobody can actually contact the customer

`SourcingTicket` stores `userId`, the message and the extraction. Staff see neither a phone number nor a name.

- **Signed in:** the only route back is an in-app offer notification.
- **Guest:** `userId` is null, so there's no route at all, yet the guest receives the same promise.

**Needed:**
- Resolve the owner's phone for staff on signed-in tickets.
- Guests: **decided.** They sign in with the existing phone OTP before a request is submitted, with no separate phone field.
- Change "свяжется с вами" to describe what really happens. **Decided:** "Request received. We'll notify you when an offer is available", in the contract.

### C. Several parts collapse into one

The saved chat has "salon cobalt filtr moy filtr 2023", which is a cabin filter and an oil filter. Extraction has room for one `part_name`. If either word matches stock, the search reports found and the other part is silently dropped.

**Needed:** a list of parts in the extraction, with one result or ticket per part, and `all_parts_accounted` in the reply. Showing the one part that was understood isn't enough: anything short of a full account must ask the customer explicitly.

### D. Customer is told yes even if staff never hear

Telegram is deliberately fire-and-forget, which is right for chat speed. But a failed send is only logged. If Telegram is down or misconfigured, the ticket waits unseen in the console while the customer has been promised 15 minutes.

**Needed:** record delivery state on the ticket, retry through a queue, and alert on tickets nobody has picked up. Production should also confirm `TELEGRAM_DEALERS_GROUP_ID` is set, because the notifier stays silent when it isn't.

### E. Duplicate check is too loose and too tight

`findRecentDuplicate` matches status `PENDING`, the last 10 minutes and exact `part_name`.

| Case | Result |
|---|---|
| Same customer, same part, **different car** within 10 minutes | Second request is dropped, because the vehicle isn't compared |
| **Two different guests** ask for the same part | Second gets the confirmation but no ticket of their own |
| **A guest asks for a part a signed-in customer just requested** | Guest is matched to that customer's ticket, because guest searches aren't scoped by user |
| Same request, **worded differently** | Model output differs, so staff get a second ticket and message |
| Same request **after 10 minutes**, or once staff move it past `PENDING` | New ticket and new staff message |
| **Two sends at the same moment** | Both can pass, since nothing enforces uniqueness |

**Needed:** include the vehicle in the comparison, keep guests separate, and consume the idempotency key the app now sends. The key does nothing until then. A longer app timeout doesn't protect against duplicates either; the open cases are in the contract under "Timeout and retry".

### F. Reply language

Language is detected from the current message only. In the saved chat, an Uzbek conversation got a Russian reply after the customer typed just "Salon". English also falls back to Russian. **Needed:** accept the app's language, or use the conversation's.

### G. Vehicle matching

The search uses `part_name` only, so the backend can't confirm a part fits. **Needed:** accept a garage vehicle ID, filter by real compatibility, and stop returning parts for other cars as "подходящие".

### H. Missing tests and visibility

- `AiChatService` has no tests, although it holds the rule that this message means a ticket exists.
- `/health` has no version, so the deployed code can't be identified from outside.

### I. Confirm with the business

The Telegram card sends the customer's raw message and any VIN to the dealers group. Confirm this is intended and covered by the privacy policy.

## Live test: blocked

**No live requests or dealer notifications yet.** This replaces the shorter test proposed in the first version of this report. The steps are in the contract under "Live test", and all of these must be true first:

- [ ] Backend authentication enforcement and request-ID deduplication are deployed, and the deployed commit is confirmed
- [ ] Date and time agreed between the owner and backend owner
- [ ] Dealers group told in advance that a test is coming
- [ ] A named staff member is ready to return an offer
- [ ] Test account agreed, with a clearly labelled test part that isn't stocked

Once it passes, steps 4, 11, 13 and 17 can be settled. Testing the guest path is part of that run. A Telegram outage is a separate decision.
