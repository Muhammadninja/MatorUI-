  3. Hard constraints I extracted (the things schema + RN code must honor)

  Currency & pricing
  - All money is UZS, integer. Payme amounts wire as tiyin (×100): amount_tiyin: 36500000 ↔ amount_uzs: 365000. Click stays in UZS units. Frontend formatter is the
  only place soum/tiyin conversion happens.
  - Pricing fields are inconsistent across screens — some send numeric price_uzs: 185000, some send pre-formatted "price": "UZS 185 000" (search, top-featured,
  cart). The canonical wire type must be integer *_uzs; the formatted price_label is display-only. Worth normalizing before schema lockdown.

  Vehicle → compatibility (the load-bearing relation)
  - Active vehicle_id is the persistent join key. It's read from MMKV mator.garage.primary_id for synchronous cold-start use.
  - vehicleContext on /v1/search is scoping, not filtering — full corpus is searched, matched rows get a relevance boost and a per-row projection compatibility: {
  status: 'fits' | 'maybe' | 'does_not_fit', confidence, notes }. The UI badge logic depends on this exact tri-state.
  - /v1/catalog/parts?vehicle_id=... returns the same projection plus a facet bucket: facets.compatibility = { fits, maybe, does_not_fit }. Schema must expose a
  deterministic compat-resolver — likely part ↔ trim_id × year and part ↔ engine_id, per the compatibility_response (matched_trims[].years, matched_engines[],
  source: "manufacturer_oem_mapping").
  - OEM cross-refs are first-class: oem_numbers: ["96440756", "55562234"] on parts; search must hit these as exact-match boosters.

  Search
  - Two endpoints: POST /v1/search (envelope: free-text, filters, vehicleContext, locale, pageToken) and GET /v1/typeahead?q=... (suggestions can be query or product
   with a deeplink to item-detail/{id}).
  - Facet response shape is non-uniform (facetCounts.categories is a string-keyed map; appliedFilters echo-back). Frontend depends on requestId round-tripping for
  stale-response rejection.

  Cart — open contract decision (flag from backend.json itself)
  - The contract says: "should cart be server-persisted (current frontend assumption) OR client-only with cart_snapshot at order-creation time (current backend.json
  order spec)? Pick ONE." My recommendation: server-persisted (/v1/cart*) — cross-device parity, abandoned-cart analytics, promo validation server-side. The order
  endpoint can still accept a cart_snapshot as the idempotency payload at checkout. Needs your decision.

  Checkout
  - Order state machine implicit in the spec: pending_payment → (Payme/Click webhook) → paid. expires_at: T+30min on the order.
  - Two providers, identical deep-link pattern: canOpenURL → openURL(deep_link) else openURL(https_fallback). Return URLs are mator://payments/{provider}/return.
  - Confirmation arrives via either polling /v1/payments/{id} (every 2s, max 30s) or an order_paid data-only push. Frontend must dedupe — backend must guarantee both
   paths produce the same terminal state.

  MyID & transaction limits
  - transaction_limit_uzs on the user (default 0, post-MyID e.g. 50,000,000). Server-side check at order creation; client should also pre-flight to render an upgrade
   prompt instead of an error.

  Garage adapter contract
  - Backend nested DTO ↔ frontend flat Vehicle (see GarageVehicleAdapterContract). Color: backend canonical is color_hex; client legacy enum is derived. Mileage is
  km. created_at (ISO) ↔ addedAt (epoch ms). All adapters live in services/garage-api.ts.

  Realtime
  - Single multiplexed WS wss://api.mator.uz/realtime?channel=garage:{user_id}, 30s ping / 45s pong timeout, exp-backoff. Events apply locally to cache; snapshot
  triggers full refetch.
