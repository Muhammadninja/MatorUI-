This document covers every API endpoint needed to power the Profile tab and all
screens reachable from it. Base path: /api/v1
Authentication: Bearer token in Authorization header for all endpoints.

Screens covered:
  - Profile (tab)
  - Edit Profile
  - Order History
  - Shipping Addresses
  - Settings & Security
  - Notification Settings
  - Payment Methods
  - Recently Viewed (also on Search tab)
  - Privacy & Security (bottom sheet)

--------------------------------------------------------------------------------
1.  USER PROFILE  —  GET /api/v1/me
--------------------------------------------------------------------------------
Purpose:
  Fetches the authenticated user's profile. Called on app mount and on
  pull-to-refresh on the Profile tab.
  Frontend hook: useUserContext().refreshProfile()

Response  200 OK:
  {
    "id": "string",             // UUID
    "firstName": "string",
    "lastName": "string",
    "username": "string",       // e.g. "m.abdullaev"  (no leading @)
    "email": "string",
    "bio": "string|null",
    "avatarUrl": "string|null", // fully-qualified URL or null
    "isPremium": true,
    "memberSince": "2024-03-15T00:00:00Z"  // ISO 8601
  }

Frontend usage:
  - Hero card: displays firstName + lastName as full name, first initials as
    avatar fallback, isPremium drives the gold star vs. grey shield badge.
  - Settings & Security: email shown next to "Change Email" row.
  - Edit Profile: pre-fills all form fields.

--------------------------------------------------------------------------------
2.  UPDATE PROFILE  —  PATCH /api/v1/me
--------------------------------------------------------------------------------
Purpose:
  Partial update from the Edit Profile screen.
  Frontend calls this when the user taps the ✓ header button or "Save Changes".
  Frontend hook: useUserContext().updateProfile(patch)
  The frontend does an optimistic local update and rolls back on error.

Request body (JSON, all fields optional):
  {
    "firstName": "string",
    "lastName": "string",
    "username": "string",       // without leading @
    "bio": "string|null",
    "avatarUrl": "string|null"  // URL after a separate upload (see §3)
  }

Response  200 OK:
  Full UserProfile object (same shape as §1)

Error responses:
  409 { "error": "username_taken", "message": "..." }
  422 { "error": "validation_error", "fields": { "username": "too short" } }

--------------------------------------------------------------------------------
3.  AVATAR UPLOAD  —  POST /api/v1/me/avatar
--------------------------------------------------------------------------------
Purpose:
  Uploads a new profile picture from the Edit Profile screen (camera badge).
  The frontend sends the image as multipart/form-data, then stores the returned
  URL and calls PATCH /api/v1/me with { avatarUrl }.

Request:
  Content-Type: multipart/form-data
  Field name: "avatar"
  Accepted MIME types: image/jpeg, image/png, image/webp
  Max size: 5 MB

Response  200 OK:
  {
    "avatarUrl": "string"   // fully-qualified URL to the stored image
  }

Error responses:
  413 { "error": "file_too_large" }
  415 { "error": "unsupported_media_type" }

--------------------------------------------------------------------------------
4.  ORDER HISTORY  —  GET /api/v1/me/orders
--------------------------------------------------------------------------------
Purpose:
  List of past orders shown on the Order History screen.

Request query params:
  page    number  default 1
  limit   number  default 20
  status  string  optional — filter by: "Delivered" | "In Transit" |
                             "Processing" | "Cancelled"

Response  200 OK:
  {
    "orders": [
      {
        "id": "string",         // e.g. "ORD-8821"
        "date": "string",       // formatted display date, e.g. "May 28, 2026"
                                // OR return ISO 8601 and let frontend format
        "status": "string",     // "Delivered" | "In Transit" | "Processing" | "Cancelled"
        "itemCount": 3,
        "total": "string",      // formatted, e.g. "$486.00"
        "summary": "string"     // short text, e.g. "Garrett GTX3582R + 2 items"
      }
    ],
    "pagination": {
      "page": 1,
      "limit": 20,
      "total": 12,
      "hasNext": false
    }
  }

Status color mapping (frontend already handles this):
  Delivered  → green   #0f9d58
  In Transit → yellow  #f4b400
  Processing → blue    #4285f4
  Cancelled  → red     #db4437

  Include this endpoint so the frontend can be built out when needed.

Response  200 OK:

    "date": "string",
    "status": "string",
    "items": [
      {
        "id": "string",

6.  SHIPPING ADDRESSES  —  GET /api/v1/me/addresses
--------------------------------------------------------------------------------
Purpose:
  List saved shipping addresses. Displayed on the Shipping Addresses screen.

Response  200 OK:
  {
    "addresses": [
      {
        "id": "string",
        "label": "string",      // e.g. "Home", "Work", "Garage"
        "name": "string",       // recipient name
        "line1": "string",      // street address
        "line2": "string",      // city, state, zip, country
        "isDefault": true
      }
    ]
  }

--------------------------------------------------------------------------------
7.  ADD ADDRESS  —  POST /api/v1/me/addresses
--------------------------------------------------------------------------------
Request body:
  {
    "label": "string",
    "name": "string",
    "line1": "string",
    "line2": "string",
    "setAsDefault": false
  }

Response  201 Created:
  Full address object (same shape as item in §6)

Error responses:
  422 { "error": "validation_error", "fields": { ... } }

--------------------------------------------------------------------------------
8.  UPDATE ADDRESS  —  PATCH /api/v1/me/addresses/:addressId
--------------------------------------------------------------------------------
Request body: any subset of the address fields from §7

11. PAYMENT CARDS  —  GET /api/v1/me/payment-methods
--------------------------------------------------------------------------------
Purpose:
  List saved payment cards shown on the Payment Methods screen.
  The frontend never receives raw card numbers — only masked last4.

Response  200 OK:
  {
    "cards": [
      {
        "id": "string",
        "brand": "string",      // "VISA" | "MC" | "AMEX" | "DISCOVER"
        "last4": "string",      // e.g. "4289"
        "holder": "string",
        "expiry": "string",     // "MM/YY"
        "isDefault": true,
        "cardColor": "string|null",    // optional hex for card background
        "accentColor": "string|null"   // optional hex for decorative circles
      }
    ]
  }

--------------------------------------------------------------------------------
12. ADD PAYMENT CARD  —  POST /api/v1/me/payment-methods
--------------------------------------------------------------------------------
Purpose:
  Triggered from the "+ Add Card" button. The frontend should open a
  Stripe / payment-processor SDK sheet rather than collecting raw numbers.
  This endpoint receives a processor token, not raw card data.

Request body:
  {
    "processorToken": "string",  // token from Stripe/Adyen/etc.
    "setAsDefault": false
  }

Response  201 Created:
  Full card object (same shape as item in §11)

Error responses:
  402 { "error": "card_declined", "message": "..." }
  422 { "error": "invalid_token" }

15. SUBSCRIPTION  —  GET /api/v1/me/subscription
--------------------------------------------------------------------------------
Purpose:
  Shown in the Subscription section of the Payment Methods screen.

Response  200 OK:
  {
    "plan": "string",           // "Premium" | "Standard" | "Trial"
    "status": "string",         // "active" | "cancelled" | "past_due" | "trialing"
    "billingCycle": "string",   // "monthly" | "annual"
    "priceDisplay": "string",   // "$14.99 / mo"
    "nextRenewal": "string",    // ISO 8601 or display date
    "cancelledAt": "string|null"
  }

  Returns null subscription data if the user has no paid plan.

--------------------------------------------------------------------------------
26. DELETE ACCOUNT  —  DELETE /api/v1/me
--------------------------------------------------------------------------------
Purpose:
  "Delete Account" danger row inside the Privacy & Security bottom sheet.
  Should require the user to re-authenticate (confirmation password/OTP)
  before the account is deleted.

Request body:
  {
    "confirmPassword": "string"
  }

Response  200 OK:
  {
    "message": "Account scheduled for deletion.",
    "deletedAt": "string"   // ISO 8601 — actual deletion after grace period
  }

Error responses:
  401 { "error": "wrong_password" }

--------------------------------------------------------------------------------
27. SIGN OUT  —  POST /api/v1/auth/logout
--------------------------------------------------------------------------------
Purpose:
  "Sign Out" row at the bottom of Settings & Security.
  Invalidates the current refresh token server-side.

Request body:
  {
    "refreshToken": "string"
  }

Response  200 OK:
  {
    "message": "Logged out successfully."
  }

================================================================================
  COMMON ERROR SHAPE
================================================================================

All errors:
  {
    "error": "snake_case_code",
    "message": "Human-readable description",
    "fields": { ... }   // optional, for validation errors
  }

HTTP status codes used:
  200 OK, 201 Created, 204 No Content
  400 Bad Request, 401 Unauthorized, 402 Payment Required
  403 Forbidden, 404 Not Found, 409 Conflict
  413 Payload Too Large, 415 Unsupported Media Type
  422 Unprocessable Entity, 500 Internal Server Error

================================================================================
  INTEGRATION NOTES FOR FRONTEND
================================================================================

1. All TODO stubs are in contexts/user.context.tsx. Each function has a comment
   showing the exact endpoint to call:
     refreshProfile()  → GET  /api/v1/me
     updateProfile()   → PATCH /api/v1/me

2. The frontend uses optimistic updates for profile edits. If the API returns
   an error, the state rolls back automatically — no extra work needed on the
   frontend side.

3. Notification toggle state is currently local (useState). Once §17/§18 are
   ready, replace the useState initial values with a useEffect that calls
   GET /api/v1/me/notifications, and fire PATCH on every toggle change.

4. Payment card colours (cardColor, accentColor in §11) are optional. The
   frontend has fallback colours (#0d0d0d, #0f0c29) if the API omits them.

5. The Privacy sheet (§24–§26) is currently a static UI. Wire it up once the
   endpoints are available — no frontend structural changes needed.

6. For security operations (change email, change password, delete account)
   the frontend will need a password confirmation modal — not yet built.
   Coordinate with the frontend team before implementing.
