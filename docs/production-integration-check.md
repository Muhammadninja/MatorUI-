## Избранное: необходимое отдельное backend-изменение

В доступной актуальной схеме/контроллерах backend нет favourites/likes-модели или маршрутов. Это также явно указано в `Backend/docs/RELEASE_CHECKLIST.md` и `src/user/account-deletion.service.ts`. Реальные GET `/v1/favorites`, `/v1/likes`, `/v1/me/favorites` вернули 404. `/docs-json` защищён (401); наличие неизвестного API за другой закрытой схемой этими запросами не исключается. Текущая реализация приложения — только `likes:v1` в AsyncStorage, без владельца и синхронизации.

Необходимый контракт (не реализован и не развёрнут в этом изменении):
- Таблица избранного с `userId`, `partId`, `createdAt`, уникальностью `(userId, partId)`, индексом для пагинации и очисткой при удалении аккаунта. Нужна отдельная миграция, сначала локальная проверка.
- Авторизованные GET `/v1/me/favorites` с курсором, идемпотентный PUT `/v1/me/favorites/:partId` и DELETE того же ресурса. Владелец только из JWT, проверка существования детали; без передаваемого клиентом userId.
- Затем HTTP-транспорт приложения, кеш по ownerId, изоляция гостя, отмена старых ответов при выходе/смене аккаунта, оптимистический откат одной записи. Старое избранное без владельца нельзя автоматически приписывать новому аккаунту или затирать им серверные записи; нужна явная политика миграции/объединения.
- Проверить права, дубли/повторы, страницы, offline и смену аккаунта; затем deployment backend и интеграционная проверка. В этом этапе избранное пользователя, его данные, реальные заказы и платежи не изменялись.
