# Единый список оставшихся пунктов MATOR

Обновлено 2026-11-03. Это актуальный рабочий список: шесть ранее согласованных зависимостей и замечания нового read-only разбора sourcing. Перечни в прежних аудитах — история наблюдений, а не параллельные списки задач. Объединённая версия сохранена в постоянной ветке `integration/approved-design-functionality-2026-11-03`, на базе утверждённого дизайна `44b7d28`. OTP autofill и посторонние незакоммиченные изменения не включены. Готовность frontend к релизу **не объявлена**.

Исправление order tracking и его доказательства: [ORDER-PRICING.md](ORDER-PRICING.md). Серверная арифметика проверенного заказа сходится; недостающие значения никогда не выводятся из разницы. Повторная проверка исправленной разбивки в native пока не выполнена из-за параллельной работы пользователя в симуляторе.

| ID | Пункт / текущий статус | Ответственный | Условие закрытия |
|---|---|---|---|
| R1 | **Favorites backend sync — заблокировано, поддержка API не подтверждена.** Локальный показ избранного и исправление быстрых нажатий не являются проверкой синхронизации. | Backend-сотрудник: API и версия развёртывания; Codex: интеграция существующего sync-кода. | Сотрудник подтверждает развёрнутый owner-scoped контракт; авторизованный GET возвращает ожидаемую схему вместо исторического 404. Затем интегрируется одна существующая реализация sync с archive-only legacy; проверяются сохранность, рестарт и отсутствие переноса данных между владельцами на разрешённых существующих сессиях. Legacy likes не импортируются автоматически. |
| R2 | **Переключение аккаунтов — не проверено на текущем real API.** Unit-тесты прежних проверок прошли. Новый разбор выявил device-global историю чата без owner scope; её изоляция не реализована. | Codex; владелец предоставляет две разрешённые существующие сессии. | Без отправки SMS агентом выполнен A→B→A/guest на согласованных сессиях: чужие адреса/заказы/платежные методы/уведомления/корзина/гараж/избранное/история чата не появляются и не отправляются в LLM; старые async-ответы не восстанавливают данные A в B. Проверены восстановление и выход; исходные данные сохранены. Зависимость избранного R1 не считается закрытой раньше API. |
| R3 | **Ошибки изменения данных — live не проверены.** Защита pending/rollback/confirmation проверена целевыми unit-тестами. | Codex; backend-сотрудник предоставляет безопасный реальный сценарий отказа до записи. | На существующем API подтверждены отказ/таймаут и корректный pending/rollback/сообщение для согласованных обратимых действий. Успех не показывается до подтверждения. Исходные данные восстановлены; нельзя специально менять статусы прочтения, если восстановление не предусмотрено. Без production-заказов/платежей, mock-ответов или локального backend. Недоступный сценарий остаётся непроверенным. |
| R4 | **Версия backend поиска — не установлена; исторические sort/cursor/OEM дефекты требуют подтверждения после деплоя.** | Backend-сотрудник: фактически работающий SHA/версия и деплой; Codex: проверка frontend-контракта. | Получены версия/SHA реально запущенного API и подтверждение развернутого исправления. На существующем каталоге повторены точные OEM/сортировка/фильтры/пагинация запросы из [BACKEND.md](BACKEND.md), без потерь и повторов страниц. Успешный поиск/категорийный фильтр сам по себе не закрывает этот пункт. |
| R5 | **Идемпотентность заказа — backend-гарантия не подтверждена.** Клиентская блокировка дублей не является гарантией при повторе/перезапуске/другом устройстве. | Backend-сотрудник: гарантия и доказательства; Codex: соблюдение контракта клиентом. | Согласован контракт стабильного ключа попытки и срока его действия; сотрудник предоставляет воспроизводимое подтверждение, что потеря ответа, повтор и конкурентная отправка не создают второй заказ и возвращают тот же результат. Подтверждённые backend-проверки в безопасной среде сотрудника отделяются от live frontend-проверок. На аккаунте владельца production-заказы/платежи для этого не создаются. |
| R6 | **Размещение входа в VIN Finder — не подтверждено.** Garage→«Добавить по VIN»→Back проверено ранее; это другой маршрут. | Claude и владелец продукта: утверждение места/подписи; Codex: маршрутизация и проверка. | Утверждено конкретное место входа в standalone VIN Finder. В объединённом текущем приложении проверены вход, Back и fallback без тупика; RU/UZ/EN подписи и доступность сохранены. Наличие маршрута/deep link или unit-тестов Back не считается подтверждённым размещением входа. |
| R7 | **Sourcing: receipt, развёрнутая версия, доставка сотрудникам и обещание 15 минут — live не подтверждены.** Текст канонический, не receipt доставки. | Backend-сотрудник: deployed SHA, существующие ticket/dispatch записи и SLA; Codex: сохранить typed receipt/status. | По уже существующим сообщениям подтверждены intent/ticket_id/владелец/new-or-reused, DB-запись и реальная staff-доставка/ack. Обещание времени опирается на операционный срок/ответственного либо заменено честным статусом. UI не считает один текст подтверждением. Без создания заявки/уведомления в начальном разборе. |
| R8 | **Sourcing: активный автомобиль не передаётся из UI, RAG-снимок не фильтрует fitment; результаты каталога только текстом.** | Codex: payload/product IDs; backend-сотрудник: поиск и fitment. | Структурированный актуальный контекст реально отправлен и применён; найденные позиции соответствуют автомобилю и доступны по ID. Закрытие требует безопасного доказательства/существующего trace, а не наличия названия автомобиля в заголовке. |
| R9 | **Sourcing: несколько запчастей и уточнения — нет структурированного per-part процесса.** | Backend-сотрудник: extraction/контракт; Codex: уточнение и представление состояния. | Каждая запрошенная позиция отдельно извлечена/уточнена, сопоставлена или явно оформлена в запрос; частичное совпадение не закрывает весь список. Подтверждены правила неоднозначности и сохранённый результат, без придуманных деталей. |
| R10 | **Sourcing: канал связи/анонимный либо отклонённый JWT — достижимость клиента не гарантирована.** | Backend-сотрудник: auth/ownership/contact; Codex: честное состояние входа/канала. | Для существующего запроса подтверждены владелец и доступный клиентский канал. Невалидный bearer не даёт молча обещать связь с anonymous; гостевой запрос имеет подтверждённый способ получить ответ либо явно не принимает такое обещание. Телефон/контакты не публикуются в артефактах. |
| R11 | **Sourcing: failure/retry/regenerate — неполная идемпотентность и повтор истории.** | Backend-сотрудник: atomic request-id/recovery/delivery retry; Codex: стабильная попытка и корректная history/pending/error. | Повтор/потеря ответа/Stop после commit возвращает тот же owned receipt без дублей и потери доставки. Разные автомобили/владельцы не склеиваются; failed/pending состояние переживает рестарт. Существующие записи/безопасные тесты сотрудника отделены от live проверки; новых production-заявок для initial inspection не создавать. |
| R12 | **Sourcing: доставка оффера клиенту — live не проверена (GET inbox 401); ошибки offer status/currency требуют согласованного контракта.** | Backend-сотрудник: existing offer→inbox→push proof/recovery; Codex: код ошибок, валюта и автомобиль в UI. | У существующего owned оффера подтверждены inbox и доступный GET, push/provider статус либо честный fallback. Сбой inbox не оставляет недоступный оффер; 409 трактуется по коду, не как безусловное accepted/expired. В начальном разборе офферы не создавать и accept/reject не нажимать. |

Изменять статус можно только с указанием проверенного commit SHA, среды, фактического результата и границы покрытия. Скриншоты, JS export или unit-тесты не заменяют отсутствующую проверку real API/native. Другие старые замечания дизайна не переаудировались в этом задании и не объявлены закрытыми.

Read-only sourcing-разбор и точные запросы backend-сотруднику: [SOURCING-INSPECTION.md](SOURCING-INSPECTION.md). Изменений реализации в этом разборе нет.
